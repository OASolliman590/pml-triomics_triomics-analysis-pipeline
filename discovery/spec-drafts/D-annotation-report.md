## 1. Problem statement, scope and contribution limits

The analyst needs to interpret both per-block statistical results and integration results without losing features, confusing identifier namespaces, inventing molecular specificity or equating inaccessible annotation with absent biology. A report must make analysis provenance and uncertainty readable even when every external route is unavailable.

D receives candidate nominations and approved evidence inputs from B/C, resolves identifiers and associations through conditional resource adapters, performs only explicitly configured and contract-compatible enrichment, and renders a full-pipeline local report from immutable A/B/C/D artefacts. A report with every annotation route disabled must still explain preprocessing, design, statistics and integration, including unavailable analyses and their limitations. It never recalculates A preprocessing or B/C models, infers sample pairing, or chooses new contrasts on behalf of the design resolver. Three built-in assay profiles are not a routing constraint: routes depend on identifier namespace and declared annotation route, while block labels remain display/provenance keys. Two, three and five blocks use the same contracts.

Both B and C feed both the gene-product/reaction interpretation route and the lipid interpretation route. A candidate's source branch does not select its molecular route. GO gene-product functional annotations are distinct from a reaction network; neither a pathway membership nor a predicted enzymatic activity establishes causality.

The closest orchestration precedent is MultiOmicsIntegrator, whose docs include lipidr-enabled class enrichment, saturation plots and pathway interpretation. OmicsAnalyst accepts lipid measurements in an official example; current 2.0 docs do not establish a dedicated lipid chemistry profile. GraphOmics supplies Reactome-linked exploration. MOFA2 supplies model-based feature-set enrichment; mixOmics supplies multilevel handling and interpretation plots. These are documented capabilities, not verified runtime comparisons. The proposed contribution is auditable contracts, explicit study-design and molecular-resolution limits, reproducible conditional annotation and transparent reporting. It is not a new enrichment method and has no established exhaustive novelty or superiority claim. [D review, D-R01–03](../reviews/D-evidence-review.md)

Proceed with a local report and route-status/accounting design while resource access is investigated. Narrow a particular analysis when its identifier resolution, valid reference set or compatible design is missing. Defer a resource adapter when rights or execution cannot be established; reopen it with the evidence specified in section 4. Deferral does not cancel D or count as completed implementation. Any accepted deferral of the ultimate user goal requires maintainer disposition.

Out of scope: raw spectra or identification engines; reidentification of metabolites; experimental inference of enzyme flux; automatic external uploads; web application hosting; a promise to annotate every feature; clinical interpretation; copying reference databases into Git by default.

## 2. User stories

1. As an analyst, I want statistical and integration candidates shown with their original identities, so that I can trace every interpretation.
2. As an analyst, I want matching identifiers in different namespaces treated separately, so that unrelated features do not merge.
3. As a lipid analyst, I want sum composition distinguished from exact structure, so that the report does not invent chains or isomers.
4. As a researcher with several blocks, I want each declared namespace routed consistently, so that adding a block does not need new branch-specific code.
5. As an analyst, I want duplicate nominations linked to one measured feature, so that evidence is not double-counted.
6. As an analyst, I want ambiguous and unmapped candidates retained, so that limited database coverage is visible.
7. As an institutional user, I want resource access gated by recorded rights, so that a client package is not mistaken for a database licence.
8. As a confidential-data user, I want local execution and explicit network boundaries, so that analysis does not silently leave the host.
9. As an analyst, I want a report when a resource fails, so that completed B/C work remains inspectable.
10. As an analyst, I want eligibility, ranks and enrichment backgrounds reported separately, so that an enrichment result has a defined comparison.
11. As an integration user, I want factor sign and selection provenance shown, so that loadings are not called abundance effects.
12. As a paired-study analyst, I want the exact contrast and analysis unit preserved, so that annotation does not reinterpret differences as independent samples.
13. As a continuous-outcome analyst, I want an incompatible BioPAN route marked unsupported, so that no artificial groups are created.
14. As a reviewer, I want resource release, parameters, licences and mapping losses, so that the run can be assessed.
15. As a user opening a report offline, I want readable tables and embedded supported assets, so that the report is usable without network calls.
16. As a maintainer, I want restart-safe artefacts, so that interrupted annotation does not silently mix resource releases.
17. As a security-conscious user, I want IDs and metadata rendered as text, so that data cannot inject executable HTML.
18. As a reviewer, I want no-hit results distinguished from errors and pending validation, so that uncertainty is not disguised.

## 3. Owned interfaces, input/output schemas and invariants

### Existing contract boundary

The supplied candidate feature set and IntegrationResult do **not** presently supply everything needed by every enrichment method. IntegrationResult contains scores, loadings, variance, selected, backend and params. A native MOFA object is not guaranteed. Selected IDs or full loadings do not substitute for native model/data inputs to `MOFA2::run_enrichment`. No hidden native-object access is allowed.

Three alternatives require an orchestrator ADR: enrich before conversion to the common integration result; extend an approved evidence contract to include specific immutable model/data inputs; or use a separately justified rank-based adapter whose inputs are available. This draft chooses none. Candidate lookup and report status are well-defined while enrichment-specific contracts remain blocked. [Independent D review D-R03](../reviews/D-evidence-review.md)

### Full-pipeline report content contract (proposed; requires A/B/C agreement)

The report consumes immutable, versioned exported stage artefacts through SourceResultIndex. Each reference carries its producing run/stage, schema/version, digest, local location, availability/reason and design/analysis identifiers. The approved export contracts must expose the following content; these requirements do not silently add fields to BlockProfile or IntegrationResult or authorize reading native backend internals. An absent export is an explicit contract gap, never a reason for the renderer to recompute a result. Essential sections and their status remain visible even when no candidate is selected or annotation succeeds nowhere.

| Section / immutable source | Required embedded report content | Missing/uncertain content behavior |
|---|---|---|
| Run and configuration / A resolver and all stage manifests | Input/block inventory and hashes, sample/subject/analysis-unit counts permitted by disclosure policy, profile and matrix identities, outcome/contrast definitions, stage/dependency versions; every effective parameter with supplied/default/resolved origin and applicable profile/version. | Missing identity or contradictory run/design references prevents a complete report and names the contract error; a safe diagnostic report may render. Unknown provenance is labeled unknown, never reconstructed from current defaults. |
| A preprocessing / exported QC summaries and transformation ledger | Per-block sample/feature flow and exclusions with reasons; missingness/QC before and after filtering; normalization method, scale, reference set/standards and assumptions; transform and imputation method/order, masks/count summaries, seeds and sensitivity provenance; matrix lineage used by B/C and diagnostics supporting declared decisions. | Missing QC, unperformed sensitivity or unavailable masks have separate section states and reasons. Never infer measured zeros, imputed values or assay units from a final matrix. No participant-level data are added beyond the approved allowlist. |
| B statistical inference / exported design, models and complete result/sensitivity tables | Study design and resolved pairing/analysis unit; declared analysis population and any change to it, with the applied incomplete-visit policy stated explicitly; model/formula, coefficient or omnibus meaning, exact contrast and direction, covariates and estimability diagnostics; full-result effect/SE/statistic/p/q/count meanings and per-block adjustment family; directional consistency numerator/denominator, exclusions and threshold definition; sensitivity methods, rank/result agreement and disagreements with limitations. | Counts alone cannot substitute for the population/estimand statement. Nonestimable/unsupported analyses, undefined SE or direction, missing counts and unrun sensitivity are explicit. D preserves B-approved scalar/vector/count semantics; it invents no effect, pooled q or sensitivity result. Complete rows remain in exports when core tables are bounded. |
| C integration / exported comparison, fit and validation summaries | Approved representation and backend; baseline comparison under matched design/input conditions; scores/loadings and variance or backend-specific score meanings, units and component orientation; tuning grid/selection criterion, subject-aware folds and fit/transform provenance; selection stability, seed/restart stability, convergence/warnings and uncertainty, including omitted diagnostics and validation scope. | No shared variance meaning or predictive validity is inferred across backends. Missing native diagnostics become unavailable with reason. Unrun baseline/tuning/stability checks are planned/not-run; unavailable methods cannot be portrayed as inferior or complete. |
| D interpretation / mapping, enrichment and accounting outputs | Both candidate origins and routes, structural resolution and ambiguity, eligible-universe/rank/model contract, null/statistic/multiplicity meanings, mapping losses/denominators, resource/version/rights, no-hit versus failed/unavailable states and uncertainty. | Annotation absence does not hide A/B/C. No biological absence claim follows from an unavailable route, unresolved mapping or invalid enrichment input. |

Each required section has `complete`, `partial`, `not_run`, `not_applicable`, `unavailable` or `invalid` status with a reason and immutable source references. These are report-section states, distinct from route states. `not_applicable` needs a producer-supplied design/method reason; optional disabled analyses are not silently considered validated. A required section whose status is neither complete nor justified not_applicable makes report completeness partial/invalid according to the approved CLI policy. A document can render successfully while the analysis is incomplete. The summary must expose that distinction and the effect of missing evidence on interpretation. Exact upstream schemas, required diagnostics by profile/backend and disclosure rules remain approval gates.

Results from different tests are never merged into one q-value merely because they share a pathway. Proposed enrichment adjustment scope is an explicit analysis family keyed by source analysis, originating block and resource/test. Coalescing records for biological display never coalesces statistical observations silently.

## 6. Architecture, provenance, restart and resources

Proposed workflow: validated evidence references → immutable feature/nominations join → rights/resource gate → namespace mapping adapters → association tables → method-specific enrichment gate/adapters → accounting validation → machine-readable outputs and CLI state (milestone 7); then immutable A/B/C/D report exports → trusted report view model → local renderer → report manifest/integrity finalization (milestone 8); then end-to-end vignettes (milestone 9). Early report specification is permitted; production report code does not begin before milestone 8. Test the highest shared boundary: D inputs to artefact bundle and externally visible state. Adapter checks cover only substantive resource-specific assumptions that the bundle test cannot isolate.

D does not reach into B/C internals; only approved input contracts/references cross the boundary. Local templates are trusted package assets. Result IDs, descriptions, sample labels and database text are untrusted content: HTML-escape them, prohibit raw HTML execution and script-bearing URLs, use an allowlist of ordinary reference-link schemes, and reject path traversal in output/resource paths. Do not inject IDs into shell commands or executable template fragments. Log/report error messages must redact credentials and not disclose participant-level metadata beyond the approved allowlist.

Restart proposal: one route/analysis artefact directory keyed by input digest, config digest, adapter version and resource hashes.
