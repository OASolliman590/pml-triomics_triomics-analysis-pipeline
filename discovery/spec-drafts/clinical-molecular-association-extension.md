# Clinical metadata and molecular associations — proposed shared extension

Date: 2026-09-06. User request: inspect the three projects' different metadata, derive granular scientific objectives and make the pipeline associate patient clinical information with molecular findings. Status: **clinical-association scope approved by the user on 2026-09-06; bounded shared design/method choices settled through Opus–Sol/Astra; empirical and implementation gates remain pending**. See the [approval record](../operations/clinical-scope-approval.md). The [local audit](../research/clinical-metadata-design-audit.md) separates observed fields from missing/unverified metadata. [Primary-source evidence](../research/clinical-association-evidence.md) supports design constraints. The [actual Opus review](../reviews/opus-clinical-extension-review.md) and [root response](../reviews/opus-clinical-extension-response.md) record this extension's separate review; final root corrections were locally checked, not independently re-reviewed.

The [adopted settlement](../operations/contract-settlement.md) now fixes common-schema ownership, service seams, representation and failed-family handling. For an otherwise valid declared family, adjustment uses internal p=1 for failed/non-estimable tests with published p/q unavailable and complete disposition counts; invalid selection/model/dependence assumptions still withhold q. Existing draft decision labels below are superseded to that extent.

## 1. Intended behavior and scope

Clinical metadata becomes a first-class typed input and objective registry, rather than merely group labels or annotations on a heatmap. Each Study retains its own variables, units, visits and questions. The service associates clinical variables with individual molecular features, approved derived molecular endpoints, MOFA/integration scores and eligible patient-level pathway scores. Drug-target evidence can reference these associations without upgrading association to binding, causal effect or independent validation.

Support different measurement inventories without assuming every Study has glucose, disease severity or body composition. A field's presence, nonmissing measurements, verified meaning and model eligibility are separate states. A source with only group labels cannot acquire unobserved laboratory measurements from its project name. Objective suggestions are explicitly proposals, not reconstructed original protocols.

Clinical metadata stays outside omics assay matrices by default. Using a clinical endpoint as an integration input while testing/predicting that endpoint requires an explicit alternative design and leakage analysis; no accidental clinical Block. Administrative/name/contact fields never become predictors by default. Subject-level review outputs, if requested and authorized, are local pseudonymized research artifacts, not clinical diagnoses or treatment recommendations.

## 2. Metadata model, source roles and variable meaning

Extend the single source-role registry with `clinical_metadata`, distinct from measurement_matrix, imported_result and other existing roles. This role is ineligible for an omics assay. Within clinical sources, declare columns/regions as identity, visit/time, observed clinical value, coded questionnaire, derived index, reference range, administrative/collection flag, summary or excluded. An InBody estimate, laboratory analyte, questionnaire response and reference limit must not share an implicit measurement meaning.

| Public artifact | Required fields |
|---|---|
| ClinicalVariableDictionary | study_id, variable_id, original label/source position, verified meaning/concept, data type (continuous/binary/nominal/ordinal/count/date/multi_response/text), units and conversion provenance, code/label and missing-code map, reference level/order, measured/derived/device-estimated/status role, allowed model roles, collection period/recall window, privacy class, verification state and evidence |
| SubjectRegistry | Study-scoped pseudonymous subject key and approved source-identity links; direct identifiers remain in a separately controlled local mapping, not model matrices or routine exports |
| VisitRegistry | Study/subject/visit key, event label, collection time/relative interval and source; baseline/follow-up definitions and ordering evidence |
| ClinicalObservation | observation_id, Study/subject/visit or explicit subject-static scope, variable_id, typed value or missing reason, value cardinality and coded response set tied to a versioned option list, qualifier/comparator and detection or quantitation limit with censoring direction, specimen/time/assay/device context, source cell/record reference and hash, provenance; no raw patient values in Git or delegate inputs |
| ClinicalSampleLink | clinical observation/visit → specimen/sample/analysis-unit relationship, join cardinality, time-window rule, matched source/metadata hashes, authorized decision and unmatched/ambiguous status |
| ClinicalDerivedDefinition | variable_id, formula/method version, exact input variable IDs, units, parameters, temporal alignment, intended interpretation and dependency group; cached source formula status separately recorded |
| ObjectiveRegistry | objective_id/version, Study/analysis, scientific question, mode/estimand, clinical and molecular roles, endpoint construction/selection ancestry, time window, target population, adjustment rationale, missingness, model/representation and multiplicity policy, confirmatory/exploratory status with declaration/data-access evidence |

Keep source code/value and proposed interpretation separate. Arbitrary codes 1/2/3 are not numerical distances or yes/no until the codebook verifies them. Multi-response and free-text entries require a reviewed structured mapping or remain nonmodelable. A mislabeled/ambiguous abbreviation stays unresolved. Gender/sex semantics follow the source definition, not an inferred binary conversion. Units are not inferred from magnitude. Source normal ranges are reference metadata, not additional observations or automatically adopted diagnostic thresholds.

Multi-select answers remain sets, never a truncated number or unreviewed single category; indicator derivation requires a ClinicalDerivedDefinition. Qualified laboratory results retain their comparator and limit; no default substitution, numeric coercion or conversion of censoring into ordinary missingness is allowed. Subject-static variables require one authoritative value per subject and variable, with conflicts recorded for resolution. Age and other time-dependent demographics require a declared reference visit/date and recomputation policy; they are not implicitly static.

Dates/times, names and sensitive free text are used only where authorized and needed; routine reports use approved relative timing and aggregate coverage. Missing date does not authorize nearest-visit matching. Matching requires explicit time windows, tie handling, timezone/precision and cardinality. Visit labels in rows and source sheets can conflict; emit an exception and require a resolved mapping rather than overwrite. A source record can map to several eligible analyses under declared reuse, but cannot duplicate the same statistical observation within one fit.

The canonical metadata view attached to A's Study/SE is generated from these registries for a declared analysis; it is not a second independently maintained source of truth. Existing `metadata.file` remains a supported canonical import path with dictionary/source provenance. Wide and long clinical tables are normalized through the manifest with all transformations recorded. Source/field mappings are bound to exact hashes and reuse approved decisions without asking repeatedly.

## 3. Objective families and model contracts

| Mode | Question | Required analytical distinction |
|---|---|---|
| `between_person` | At a defined visit/window, how do molecular endpoints vary with clinical status across patients? | Explicit visit/patient population, response/predictor direction, units and justified covariates. Repeated visits cannot be pooled as independent patients. |
| `within_person` | Does a patient's clinical change accompany molecular change? | Pair/visit identity; declared delta or repeated model; separate within-person from between-person components when appropriate; covariance/time assumptions explicit. |
| `baseline_to_later` | Does baseline status associate with later molecular/clinical state or change? | Baseline-only predictors, follow-up horizon, exact outcome/change definition and baseline-adjustment choice; mathematical coupling/regression-to-mean concerns recorded. |
| `effect_modification` | Does an exposure/group/time association differ by a clinical characteristic? | Prespecified interaction, estimable joint design, adequate support and contrast definition; subgroup significance differences are not themselves interaction evidence. |
| `prediction` | Can available clinical/molecular information predict an unseen patient's endpoint? | Information available at prediction time; nested training/evaluation, patient-disjoint and temporal partitions as required; held-out performance/uncertainty versus association p values. |

Every objective declares which variable is response and which is predictor. Feature-as-response models, clinical-outcome-as-response models, correlations and predictions are not interchangeable. The existing limma-style continuous molecular-response service can be reused only for compatible approved designs. Binary/ordinal/count clinical responses, nonlinear patterns, time-to-event or other new families remain explicit method contracts; no silent conversion to continuous regression, arbitrary dichotomization or Pearson correlation. Unsupported family yields a visible unavailable objective until reviewed; its clinical scope is not silently dropped.

For repeated observations, distinguish a predictor's within-person deviation from its between-person level when needed and account for time trend/unbalanced follow-up. Subject-centering alone is not a universal covariance or confounding solution. Required model rank, residual support, sparse categories, separation, influential observations and convergence checks are method-specific; no universal sample-size cutoff or automatic fallback is prescribed. Constant fields receive not-estimable status rather than manufactured effects. Subject counts, actual fit rows and clinical/molecular complete pairs are distinct output quantities.

## 4. Adjustment, derived variables and missingness

Assign covariates by objective: exposure, outcome, plausible pre-exposure confounder, effect modifier, mediator/consequence, technical nuisance or descriptive-only. Record causal/temporal rationale even when the claim remains associational. Do not fit every available column, select covariates by significance or silently adjust for a downstream mediator. Source units, collection windows and device batch can matter. A covariate used as preprocessing nuisance cannot be tested later as though its signal were retained.

Derived endpoints retain parent relationships. Weight/BMI/body-fat indices and glucose/insulin/derived resistance indices can be strongly related by construction; do not treat all as independent corroboration, or include algebraically dependent predictors without a reviewed model. A formula labelled HOMA-IR requires source-method/units verification and cannot be assigned a diagnostic cutoff here. Do not use omics intensity ratios as laboratory concentration ratios.

Missingness is classified separately for clinical cells, visits, entire assays, censored laboratory values, not-collected/not-applicable responses and unresolved codes. Placeholder text is a diagnostic until the missing-code rule is approved; zero is not automatically missing. All-placeholder columns are unavailable. Clinical missing-data handling is independent of omics imputation; no shared MinProb/QRILC default. A complete-case mode is explicit, reports exclusions and resulting target population, and requires assumptions/limitations; more general imputation needs a compatible substantive model, uncertainty pooling, training-only fit where predictive and sensitivity review. Do not let each heatmap cell's different complete-case sample set go unreported.

## 5. Integration, pathway and target associations

Use an `AssociationEndpoint` sidecar for each molecular/derived/score endpoint: endpoint_id, feature/block or score/component identity, Study/analysis, unit-map/representation hash, producing fit and training population/outcome, transformation and orientation/scaling, selection/learned-state lineage, available-at-prediction time and dependency groups.

MOFA factor–clinical associations are supported as a planned capability. The official correlation helper is an exploratory numerical correlation utility, not the adjusted repeated-measures engine. Encode clinical categories explicitly and preserve signed effects/uncertainty. Factor sign/rotation/permutation differences across fits must be resolved for comparison; no sign is interpreted as treatment change without a defined contrast. An unsupervised label does not automatically establish independent inference after choosing a factor/endpoint using the same clinical data.

DIABLO/block.spls components are trained with outcomes. Association with that training endpoint is descriptive training fit, not clinical validation. A correlated alternate endpoint can also be affected by selection. Confirmatory association/prediction needs an appropriate independent/selection-aware protocol and held-out score construction. All learned preprocessing, variable/feature selection, score construction and tuning stay within applicable training partitions. Clinical-only, molecular-only and combined prediction comparisons use matched eligible patients, splits and metrics to assess added information.

B/C keep the same approved molecular representation within each analysis/context. A between-patient level association cannot use a representation that removed subject levels; a baseline predictor of a retained molecular change is a different permissible target if its complete design is valid. New representation choices remain protected decisions, with explicit analysis IDs and comparability records.

A pathway enrichment result from one contrast is not a patient-level pathway score. Patient associations require a separately approved `ScoreArtifact` with one score per declared unit, scoring method/weights/resource/units, fit/apply provenance and full endpoint lineage. Score generation must not use the clinical outcome under test without accounting for that learning. D's target hypotheses can reference clinical association records with support/conflict/context but cannot call them binding evidence or independent replication of the same underlying B/C observations. Clinical metadata supplies context, not an automatic explanation for every target.

## 6. Single owner for models and runtime sequence

A owns dictionaries, source validation, clinical registries/linkage and analysis metadata views. B owns ObjectiveRegistry resolution, association fitting, estimability, uncertainty/multiplicity and diagnostics. C owns integration/score construction, split plans and prediction evaluation. D owns rendering and semantic links to pathways/targets; it does not implement ad hoc clinical regressions.

B exposes one proposed public association service accepting immutable endpoint artifacts, clinical views and a resolved objective. It is implemented/tested with synthetic feature/score artifacts during B's build milestone; C is not a production prerequisite for that implementation. At runtime, A → B feature associations → C scores → B-owned score associations → D report is an explicit acyclic artifact graph. A later D-produced approved pathway score can request a new B-owned association artifact; it does not refit an earlier B/C result or create a competing modeling implementation. These callbacks require approved callable contracts and unique analysis/request IDs. D never reaches into private native backend objects.

The extra runtime invocation does not change the one-component-at-a-time implementation sequence or the protected BlockProfile/IntegrationResult fields. No actual API signature is adopted before shared review.

CL-ADR02 assigns the shared endpoint/objective/result schemas, including AssociationEndpoint, ObjectiveRegistry and ClinicalAssociationResult, to a versioned common contract artifact consumed by A/B/C/D. Its package/location and signatures require adoption before B-T08; it cannot reside in C or D or be duplicated across packages. C/D consume B's public service contract, and B consumes immutable shared-schema artifacts without importing or invoking C/D. Runtime artifact production order may include C or D before a new B association request; the orchestrator schedules those requests in an acyclic graph, rather than B calling its producers.

## 7. Result, multiplicity and eligibility contracts

`ClinicalAssociationResult` requires objective/version, Study/analysis/request/endpoint/clinical-variable IDs, response/predictor roles and estimand, effect/SE/interval with scale/units and method, statistic/p/q availability, adjustment set, model/formula/contrast, independent-patient/observation/pair counts, missingness/exclusions and analysis population, representation/endpoint construction provenance, diagnostics, sensitivity, hypothesis/selection status and resource/source hashes.

`AssociationFamily` declares fixed hypothesis members/digest and scientific claim scope across clinical variables, endpoints, contrasts and interactions before testing. Feature-level correction remains separate by Block; the expanded within-Block family accounts for the approved clinical question scope. Existing per-Block B q values do not automatically control all metadata questions. Cross-block integration factors and approved pathway scores have explicitly separate families and are never folded into a pooled molecular Block q. A global confirmatory claim needs an approved hierarchical or other valid design; separate q values alone do not support it. Record declared, evaluated, failed/non-estimable and reported member counts separately, with a disposition for every declared hypothesis. Observed rank, sparsity, missingness or fit failure cannot silently shrink the family. Eligibility rules must be prespecified; coverage/design-based filtering is data-dependent and needs a method-specific validity justification, not merely execution before p values. An approved multiplicity method must specify conservative handling of unevaluated members; without that contract no inferential q values are released. Post-hoc family changes retain the original ledger and exploratory label and require selection-valid analysis before any confirmatory claim.

Prediction has a separate evaluation ledger containing every candidate pipeline, target, split, metric, tuning/selection decision and held-out reuse across requests. Repeated inspection of an evaluation set changes its validation status. A best-of comparison cannot be presented as one untouched evaluation; final performance claims require a protocol that accounts for selection and reuse.

No ordinary re-testing from significance-selected exported lists; require full eligible source evidence and selection-valid family decisions. Prospective versus exploratory status includes request history, endpoint/factor selection and data reuse across analysis IDs. A new filename or hypothesis timestamp does not reset prior discovery. An unsupported adjusted test cannot silently become a univariate correlation. Plot-only exploratory views keep their construction/status visible and do not invent inferential p/q.

Eligibility separates dictionary validity, populated measurement availability, identity/time alignment, retained signal, model feasibility, selection validity and prediction-context validity. Proposed failures: `A_CLINICAL_DEFINITION_UNRESOLVED`, `A_CLINICAL_UNIT_UNVERIFIED`, `A_CLINICAL_JOIN_AMBIGUOUS`, `A_CLINICAL_VISIT_CONFLICT`, `A_CLINICAL_STATIC_CONFLICT`, `A_CLINICAL_MULTIRESPONSE_UNMAPPED`, `A_CLINICAL_VALUE_CENSORED_UNRESOLVED`, `B_CLINICAL_NONESTIMABLE`, `B_CLINICAL_FAMILY_UNSUPPORTED`, `B_CLINICAL_FAMILY_UNDECLARED`, `B_CLINICAL_SELECTION_UNVERIFIED`, `C_CLINICAL_TARGET_LEAKAGE`, `C_CLINICAL_REPRESENTATION_MISMATCH`, `D_PATIENT_SCORE_REQUIRED`. Unavailable objectives still appear with reason; no null clinical conclusion from missing data or a failed model.

## 8. Report and granular objectives

Report a variable dictionary and coverage map; objective cards; effect/uncertainty forest plots and signed association matrices; per-cell patient/visit counts and adjustment/population; exploratory versus evaluated score associations; matched prediction comparisons where executed; exclusions, sensitivity and unavailable variables. Group-level summaries and individual pseudonymized research views remain distinct disclosure modes. Names/contact fields and sensitive free-text values are excluded from routine outputs. Reports link each clinical association to the molecular feature/factor/pathway/target evidence with dependency provenance.

Each clinical-to-target evidence link records subject overlap, sample overlap and shared fit/selection lineage separately as full/partial/none/unknown, with provenance and approved overlap assessment. Full, partial or unknown dependence blocks independent-replication language; no overlap alone proves neither statistical independence nor binding. Reports use an approved audience-specific minimum cell size and complementary suppression to prevent reconstruction from totals; coverage maps, category counts and association plots obey the same disclosure policy. No numerical threshold is adopted here.

The local audit proposes Fasting objectives around glucose/insulin regulation, inflammation/lipid-panel measures, adiposity/lean mass/hydration, fasting duration/context, baseline-to-later association and MOFA factors. Its BP headers currently lack readings. Organophosphate and Diabetic support group/visit objectives from labels only until authoritative patient metadata is located; do not manufacture granular clinical outcomes. No hardcoded project labels, real counts or patient values enter reusable code/tests.

ObjectiveRegistry includes unavailable clinical objectives with a dated dependency request: needed field definitions/codebook, units, visit definitions, source location and authoritative clinical-to-sample key, plus owner/status and evidence searched. The local audit records the two study-specific requests. Absence of a located table is not evidence that the original study never collected the variables.

## 9. Planned validation and bounded tickets

Synthetic examples: (1) opposite between-person and within-person slopes, with permuted and missing visits; (2) a clinical outcome used to train a supervised score, showing why its training correlation cannot become fresh validation; (3) a mixed clinical workbook with codebook gaps, numeric text, placeholder-only BP, derived-index/summary rows and conflicting sheet-versus-row visit labels. Fixtures use invented sizes and values, not study constants.

Also test preserved multi-select sets and censored lab qualifiers, subject-static conflicts, fixed-family accounting after failed fits, cross-request held-out reuse, evidence-overlap labels and complementary small-cell suppression. Test ambiguous/reused IDs across Studies, stale maps, different units, window ties, multi-response codes, constant/sparse categories, rank deficiency, baseline/change coupling, missing clinical-only versus assay-only visits, derived-variable dependence, nested preprocessing leakage, correlated endpoint selection, factor sign/permutation, clinical-only versus combined prediction, false patient-score construction from contrast enrichment, and multiplicity across endpoint families. ## 10. Decisions and readiness

Proposed clinical shared-contract decision CL-ADR01 owns source/dictionary/identity/time semantics; CL-ADR02 owns objective/model/representation and association-service ownership; CL-ADR03 owns selection/multiplicity/missingness; CL-ADR04 owns score/prediction lineage and report disclosure. Link these to existing A-D01/D08, ADR-B-01/02/03/04/05, C evaluation/score decisions and D-ADR01/05/07. New source roles and artifact schemas are proposals requiring coordinated approval; no protected interface is silently widened.

Readiness requires field meanings/units/codebooks and authoritative linkages for each real objective, specified public contracts/methods, primary-source evidence, independent review and all original G0 requirements. R confirmation, dependency/resource approvals and executable verification remain open. No clinical associations, tests, implementations, package installation, commits or external publication are claimed by creating this document.
