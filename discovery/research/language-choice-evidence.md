# R versus Python for the triomics core

Date: 2026-09-06. Scope: primary/official package documentation plus the release-source inspection already recorded in [runtime compatibility](runtime-compatibility.md). This is a recommendation, not user confirmation or a tested environment.

## Recommendation

Use **R as the package, orchestration and contract language**, with **MOFA training in a separately pinned Python environment** invoked through the released MOFA2 adapter. This minimizes semantic translation at the exact methods already selected: MultiAssayExperiment/SummarizedExperiment containers, limma, DEqMS, mixOmics/DIABLO, MOFA2 and Quarto. Python remains an implementation detail of MOFA rather than a second owner of identifiers, preprocessing, statistics or reporting.

Bioconductor 3.23 is explicitly paired with R 4.6 and recommends a release-coherent installation rather than mixing repositories ([Bioconductor installation](https://bioconductor.org/install/)). MultiAssayExperiment 1.38.0 directly represents multiple assays with overlapping specimens and depends on SummarizedExperiment ([official package page](https://bioconductor.org/packages/release/bioc/html/MultiAssayExperiment.html)). The selected inferential and integration implementations are released in the same ecosystem: [limma 3.68.5](https://bioconductor.org/packages/release/bioc/html/limma.html), [DEqMS](https://bioconductor.org/packages/release/bioc/html/DEqMS.html), and [mixOmics 6.36.0](https://bioconductor.org/packages/release/bioc/html/mixOmics.html). Reimplementing their behavior in Python would change the method or require a cross-language bridge for several core stages, adding conversion and numerical-equivalence gates without a project benefit.

Python is technically viable for generic mixed models and PLS through [statsmodels MixedLM](https://www.statsmodels.org/stable/mixed_linear.html) and [scikit-learn PLSRegression](https://scikit-learn.org/stable/modules/generated/sklearn.cross_decomposition.PLSRegression.html), and MOFA’s computational core is Python. Those APIs do not by themselves reproduce the already specified limma moderation, DEqMS count-dependent prior variance, DIABLO adapter semantics or Bioconductor containers. A Python-first rewrite would therefore be a new architecture decision, not a neutral language substitution.

MOFA’s own documentation recommends the R MOFA2 interface while stating that the core is `mofapy2`; it documents a dedicated, version-pinned basilisk environment for dependency conflicts ([MOFA2 installation](https://biofam.github.io/MOFA2/installation.html)). The inspected MOFA2 1.22.0 release pins Python 3.12.12 and mofapy2 0.7.3 and calls `basiliskStart`; actual process isolation depends on the selected basilisk configuration/version and must be verified. Use those release pins first, require the chosen isolation policy to pass a runtime probe, forbid implicit first-run downloads in production, and export only versioned common artifacts back to R.

For reproducibility, an R lock is necessary but not sufficient. `renv` records exact R package versions and sources ([official renv documentation](https://rstudio.github.io/renv/)); its own documentation notes that R, OS, compiler and system libraries remain outside that lock. Acceptance therefore requires: R 4.6.x/Bioconductor 3.23 coherence; an `renv.lock`; the resolved Python lock and hashes; MOFA train/save/reload smoke tests; R–Python version checks; HDF5 compatibility; and recorded OS/compiler/BLAS/thread/RNG state.

Decision status: **R-core recommendation is evidence-ready but user-pending**. Exact patch versions and lockfiles remain **runtime-validation pending**; no package has been installed here.
